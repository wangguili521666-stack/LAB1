# 需求追踪、测试有效性和基础设施约定

## 需求基线

需求原文仍以 requirements/demands.md 为依据；requirements/traceability.json 逐项保存编号、验收条件、实现入口、验证文件、操作方法、命令、状态、责任模块及待办；baseline-ids.json 保留历史编号。辅助阅读见 requirements/traceability.md。

`npm run requirements:check` 检查漏登记、编号删除、验收缺失、标准不同步、引用失效和无证据的完成状态。unit/full CI 都先执行此检查及其负例测试。它只能验证结构完整性，不能自动判断业务实现正确。已登记清单与原文同时恶意删改仍需 Git 评审约束；评审必须查看需求删除。

新增需求：先补明确输入、前置条件、可观察结果和拒绝边界，再登记原文、JSON 与编号清单。变更需求同步更新实现和断言；废弃需求改 retired，记录原因和替代编号，不删除条目。验收后标 verified 并附 evidence 报告路径。未完成使用 partial/deferred/pending_acceptance，gap 必须写明缺口和后续动作。测试文件只是核查入口，不能当作该需求已有完整断言的证据。

当前逐条状态采取保守口径：未逐条确认的业务需求标 pending_acceptance，即使整套 CI 曾通过也不自动批量标完成。邮件/微信真实发送、M2 审计持久化重试、生产发布与回滚明确 deferred。D1 动态权限和聚合保留历史条目，同时保留后续实现入口，不能让旧待办直接消失。

## 测试确实验证行为

`npm run test:mutation` 执行五个定向变异：教室码忽略教室、取消角色限制、取消预约时长上限、关闭全天开放判断、破坏成功响应码。每项先确认原实现测试通过，再只修改临时副本的真实实现，运行相同测试。必须出现 ERR_ASSERTION 且原版有通过用例才计为捕获；语法错误、依赖缺失、超时不能算成功。变异存活、位置漂移或原版失败均令命令非零退出。每项执行后删除临时副本，原项目代码不被破坏。

先安装对应包依赖后可单独执行；推荐 `npm test` 或 `npm run test:all`，CI 自动准备依赖并执行变异。报告保存到 test-results/mutation-*/，包含原版、变异日志及 summary.json。CI 副本中的报告会随临时环境清理，捕获结果仍在外层 output.log；单独执行可保留细节。

这五项是定向质量门禁，不是全系统变异覆盖率。新增重要规则应增加对应正反例及定向变异；不能宣称所有测试已证明有效。Mock 仅用于依赖边界，不能替换被测业务判断；数据库并发和跨模块链路继续使用完整 CI 的真实服务验证。

## 基础设施脚本化

前置条件：安装并启动 Docker Engine/Compose，Node.js >=22；安装软件本身不由项目自动更改系统。

- `npm run infra:up`：复用 start.sh，首次生成本地配置，构建 MySQL、六后端和前端，迁移和种子自动执行，健康检查后成功。
- `npm run infra:status`：查看容器和健康状态。
- `npm run infra:stop`：停止本项目，保留数据库卷。
- `npm run test:all`：独立测试环境，从空库启动、两轮重放、行为变异及跨模块测试，结束清理本轮资源。
- `npm run package`：生成带校验文件的部署源码包，包含 docs、配置模板、部署和验证脚本；不含真实 .env。

已有环境升级执行 infra:up；密码保留，不清空卷。禁止使用删除卷作为升级手段。生产权限、备份、审批和回滚演练尚未落地，明确保留为 INFRA-PRODUCTION；这些不因 Docker 启动成功而视为完成。正式 CI 使用独立环境解决部署干扰，细节见 database-evolution.md。
