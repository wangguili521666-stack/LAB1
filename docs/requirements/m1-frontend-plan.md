## 3. 页面组织与实现原则

保留 `/m1` 和现有导航，先在 M1 页面内组织“找座位、我的预约、违约记录、管理”区域；管理入口以确认后的权限映射控制。新增页面组件放在 `frontend/src/components/m1/`，模块请求放在 `frontend/src/api/m1.js`，纯规则与格式化函数放在 `frontend/src/utils/m1.js`。这些路径是后续计划，第一阶段尚未创建。

请求统一调用现有 `utils/request.js`。每个查询和写操作拥有独立反馈状态。ID 保持字符串；空筛选项不传；按公共契约处理分页、401/403/409/422/503。用户看得到的时间与请求时间应表示同一校园时段，不能随客户端时区漂移。校园业务时区以组内配置为准，建议 Asia/Shanghai，待确认。

座位采用带编号、教室和插座标记的列表或卡片。不将没有坐标的数据绘制成真实座位平面图；不可从静态 AVAILABLE 推断某时段可预约。查询结果绑定当次查询条件，改动条件后旧结果不得用于新条件预约；迟到的旧请求不能覆盖新结果。

遵循现有绿色系样式，主要新增样式限定在 M1 组件内。公共路由、请求工具、样式或依赖如确需改变，明确理由并单独标注给相关负责人评审。

## 4. 阶段与交付门槛

### 第一阶段：需求与验证基线（当前）

交付本方案、[验收清单](m1-frontend-acceptance.md)、[验证记录](m1-frontend-phase1-validation.md)。给需求编号，区分已确认规则、建议、缺口；验证现有工程，不改业务代码。人工审阅只确认规划范围，不代表后续功能通过。

### 第二阶段：查询与预约

实现有效日期与整点时段、时间先后校验、最大时长规则接入、楼宇/教室/学院/插座筛选、结果展示、确认预约、重复点击防护、成功后刷新及失败恢复。最大时长默认 4 小时，但实际配置覆盖规则必须确认后接入。

验收：FE-M1-01～05、14～17。接口未到位时，可在测试/开发专用场景中使用契约样例，明确标注模拟；生产请求失败不得自动返回假数据。完成前端验证后可上传评审，真实业务验收仍标为待联调。

### 第三阶段：个人预约闭环

实现记录筛选/分页/详情、取消确认、编码签到、历史复约和违约记录。保留当前页与筛选的合理状态，服务端写入成功但刷新失败时分别反馈，不能诱导用户重复预约。

验收：FE-M1-06～10、15～17；签到时间窗口与取消规则先解决 GAP-03，再实现对应限制。

### 第四阶段：M1 管理界面

实现管理预约列表、已确认统计字段和配置编辑。权限、键名、可修改范围与统计口径确认后接入。普通用户没有管理操作入口，但真正鉴权仍由服务端完成。

验收：FE-M1-11～13、17；禁止通过伪造前端角色或硬编码统计值交付。

### 第五阶段：真实联调

使用隔离的测试账号和环境验证全流程；与 M1、D1、D2 及 M2/M3 负责人核对资源占用、维修阻塞、提醒与违约结果。模拟请求测试只证明前端行为，不证明并发控制、通知发送或资源释放。

验收：INT-M1-01～05，并回归所有前端用例。接口缺失、环境故障和业务失败分别记录，未通过项目不删除。

### 第六阶段：交付与展示

完成使用说明、测试证据、需求到实现/测试的追踪记录和已知限制；协调公共流水线执行前端构建与测试。按任务书准备实际操作演示，截图只能补充证据，不能代替系统演示。生产发布与回退由小组发布负责人协调。

## 5. 依赖和待确认事项

以下均未自动视为已批准。每项由对应负责人给出接口样例或书面结论，并记录到评审或后续契约变更。独立部分可先开发，依赖该结论的部分暂不固化。

- **GAP-01：可用座位响应与目录数据（M1/D2/D1，阶段二）**。M1 的 AvailableSeat 仍标“建议定义”；确认字段、空结果语义、是否包含不可用座位。楼宇、教室、学院的真实选项来源及访问权限待确认。`demands.md` 的 M1-01 要求座位列表和使用状态，而 M1 可用座位接口可能只返回空闲座位；不能宣称该接口覆盖全部状态。
- **GAP-02：预约参数与时间（M1，阶段二/四）**。确认最大时长的 setting_key、类型、范围、读权限、获取失败策略、校园时区、跨日和提前预约规则。已确定整点小时、默认上限 4 小时；其他限制不可自行添加。
- **GAP-03：签到与取消（M1，阶段三）**。确认可提前多久签到、截至时间及边界包含关系、重复签到响应、哪些状态/时点可取消。任务书写超时“自动取消”，API 用 NO_SHOW，前端应显示“未签到违约”并记录该对应关系供负责人确认，不能随意改为 CANCELLED。
- **GAP-04：教室动态签到码展示（M1/教室端负责人，阶段三/五）**。已有 internal/verify 是服务间校验接口，不是浏览器取码接口。确认教室屏幕的归属、取码与刷新方式、权限；前端不得生成假码或直接调用 internal 接口替代公开签到接口。
- **GAP-05：历史显示信息（M1/D2，阶段三）**。SeatBooking 只有 seat_id，没有座位名称和教室展示字段。确认聚合字段或允许的公开查询方式；不伪造名称、不对每条记录无界发起查询。
- **GAP-06：管理权限（M1/D1，阶段四）**。确认 SYSTEM_ADMIN、CLASSROOM_ADMIN、OPERATION_ADMIN 的操作与数据范围。现有 /users/me 有 roles，无 M1 细粒度权限清单；不能仅凭角色名称断言权限。
- **GAP-07：统计和分页（M1，阶段四）**。确认四个建议统计字段、按创建时间还是预约时段统计、时区和区间边界；管理列表返回分页但参数列未列出 page/page_size，需确认。没有分母定义时不展示“座位利用率”。
- **GAP-08：提醒及状态来源（M1/D2/通知负责人，阶段五）**。确认前 15 分钟/后 10 分钟通知和后 15 分钟违约的真实实现、证据来源；M1/M2/M3 写入来源如何被授权查询。现有可用座位响应没有来源字段，不能从列表消失推断来源或自动恢复原因。
- **GAP-09：工程依赖治理（前端公共负责人，阶段六前）**。仓库跟踪了 788 个 node_modules 文件，现有 Windows 克隆目录构建缺少 vite 启动入口。独立按锁文件安装后构建成功。建议单独评审停止跟踪生成依赖，用锁文件安装；本阶段未删除这些文件。

## 6. 提交、验收与职责

每一批变更按“实现/记录 → 自动验证 → 可运行预览或文档审阅 → 人工验收 → commit/push → Merge Request 评审”进行。用户已授权分阶段实施，不等于未来尚未展示的变更已完成验收。

建议提交顺序：`docs(m1): define frontend scope and acceptance`、`feat(m1): add seat search and booking`、`feat(m1): complete personal booking flows`、`feat(m1): add management views`、`test(m1): verify integration and delivery`。按实际变更拆分，测试随对应功能提交，不积攒到最后。

只暂存本阶段明确文件。上传到分支、合并主分支和部署分别报告；不自动解决有业务含义的冲突，不强推主分支。需要公共配置改动时由相关负责人评审。第一次人工审阅通过后，文档先提交上传，再进入第二阶段。

每次阶段报告给出：需求编号、实现文件、验证命令与结果、模拟/真实环境区别、未完成依赖、人工验收操作、提交与远程状态。隐私只展示必要信息，违约规则和错误反馈须可理解，重要操作可键盘访问。
