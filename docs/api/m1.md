5.4 座位预约接口
POST /api/m1/bookings
请求：
{
  "seat_id": "301",
  "start_time": "2026-10-23T09:00:00+08:00",
  "end_time": "2026-10-23T11:00:00+08:00"
}


成功响应：
{
  "code": "OK",
  "message": "预约成功",
  "data": {
    "id": "501",
    "user_id": "101",
    "seat_id": "301",
    "reservation_id": "401",
    "start_time": "2026-10-23T09:00:00+08:00",
    "end_time": "2026-10-23T11:00:00+08:00",
    "status": "BOOKED",
    "created_at": "2026-10-22T14:00:00+08:00",
    "cancelled_at": null
  },
  "request_id": "req-006"
}


接口必须满足以下条件：申请时段按整点小时计，单次预约不超过配置的上限（默认 4 小时），用户具有预约权限，座位和教室都处于可用状态，且 D2 成功建立资源占用。
M1 调用 D2 创建占用后，应将该占用确认，再将 reservation_id 存入 seat_bookings。不可以只写入 M1 预约表而不调用 D2。
5.5 签到与违约规则
签到：
POST /api/m1/bookings/501/checkin


{
  "checkin_method": "CODE",
  "code": "482916"
}


时间	系统动作
预约开始前 15 分钟	发出第一次提醒
预约开始后 10 分钟	未签到则再次提醒
预约开始后 15 分钟	未签到则标记 NO_SHOW、释放资源并记录违约
正常签到	BOOKED → CHECKED_IN
学习时段结束	CHECKED_IN → COMPLETED
提醒、动态签到码以及定时检查机制是需求文件规定的功能，但现有四张 M1 数据表没有保存提醒记录或动态签到码的字段。可以通过定时任务、缓存和通知接口实现；如果需要持久化追踪，则要补充 Schema。

## 2026-10-29 实施补充

服务认证、权限和重试边界见 [架构决策](../architecture/service-auth.md)。所有个人/业务接口需用户认证。
M1 新增内部恢复状态 CREATING / CANCELLING / EXPIRING，失败时保留并由工作器重试；客户端遇到这些状态应提示处理中，禁止重复操作。GET /api/m1/admin/checkin-code/{classroom_id} 供系统/教室管理员取得当日签到码。max_booking_hours 取值 1–24，默认 4。签到窗口为开始时刻至开始后 15 分钟（右端不含）。当前仅实现 CODE 签到。定时任务为服务内部工作器，不公开定时任务触发接口。

## 教室现场展示

GET /admin/checkin-code/{classroom_id} 需 SYSTEM_ADMIN 或 checkin:display 权限；非系统管理员只可查看自己非空学院的教室。响应包含 classroom_id、building、room_number、code、server_time、valid_until。编码与教室和北京时间日期关联，valid_until 是次日北京时间零点。响应禁止缓存。

网页 /checkin-screen 登录后可选择教室并全屏显示六位编码；每 15 秒重新校验并刷新，按服务端时间计算有效期，跨日隐藏旧码并重新获取；连接失败、权限撤销或令牌失效后隐藏编码。页面不把令牌放进 URL。采用任务书允许的 Web 数字编码方案，不实现微信扫码。
