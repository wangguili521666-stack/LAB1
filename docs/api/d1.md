
3.1 Database Schema
数据表结构直接采用上传的《数据库》文件；API 字段约定是为开发补充的建议。
数据表	字段及类型
users	id BIGINT PK, username VARCHAR(50) UNIQUE, password_hash VARCHAR(255), nickname VARCHAR(50), email VARCHAR(100), phone VARCHAR(20), college_id BIGINT FK, status VARCHAR(20), created_at DATETIME, updated_at DATETIME
roles	id BIGINT PK, role_code VARCHAR(50) UNIQUE, role_name VARCHAR(50), description VARCHAR(255)
user_roles	user_id BIGINT FK, role_id BIGINT FK, assigned_at DATETIME
permissions	id BIGINT PK, permission_code VARCHAR(100) UNIQUE, description VARCHAR(255)
role_permissions	id_role BIGINT, id_permissions BIGINT，联合主键
colleges	id BIGINT PK, name VARCHAR(100) UNIQUE
users.status：ACTIVE / DISABLED。
角色通过 user_roles 与用户关联，通过 role_permissions 与权限关联，构成标准 RBAC 模型。
3.2 对外 JSON Schema
UserPublic
{
  "id": "101",
  "username": "student001",
  "nickname": "张三",
  "college_id": "1"
}


UserPrivate 在 UserPublic 基础上增加：
{
  "email": "student@example.com",
  "phone": "13800138000",
  "status": "ACTIVE",
  "roles": ["STUDENT"],
  "created_at": "2026-10-22T09:00:00+08:00"
}


公开资料不包含手机号、邮箱、密码哈希。roles 来自 user_roles 和 roles 的关联查询。
3.3 API Contract
方法	路径	请求参数或 Body	返回 data
POST	/api/d1/auth/register	username, password, nickname, email, phone, college_id	{user_id, username}
POST	/api/d1/auth/login	username, password	{access_token, token_type, expires_in}
POST	/api/d1/auth/logout	无	{success}
GET	/api/d1/users/me	无	UserPrivate
PATCH	/api/d1/users/me	nickname?, email?, phone?	UserPrivate
PUT	/api/d1/users/me/password	old_password, new_password	{success}
GET	/api/d1/users/{id}	路径参数 id	UserPublic
GET	/api/d1/users/me/records	type?, page?, page_size?	PersonalRecords
GET	/api/d1/users/{id}/roles	id，管理员或授权服务	{roles}
PUT	/api/d1/users/{id}/roles	role_codes: string[]	{user_id, roles}
GET	/api/d1/roles	无	Role[]
POST	/api/d1/roles	role_code, role_name, description?	Role
PUT	/api/d1/roles/{id}/permissions	permission_codes: string[]	{role_id, permissions}
GET	/api/d1/permissions	无	Permission[]
GET	/api/d1/colleges	无	College[]
POST	/api/d1/internal/authorize	user_id, permission_code, resource_college_id?	{allowed, reason}
其中：
- Role = {id, role_code, role_name, description}
- Permission = {id, permission_code, description}
- College = {id, name}
- PersonalRecords = {seat_bookings, classroom_applications, repair_tickets}，每个字段为分页业务记录集合。
PUT /users/{id}/roles 采用整体替换角色集合的语义。只有系统管理员可以调用，不允许普通用户修改角色。
登录后的 Token 采用 JWT 时，退出登录仅清除客户端凭证不一定能立即使已签发 Token 失效。如要求服务端立即撤销，需要额外的令牌撤销机制，现有数据库没有对应表。
3.4 跨模块接口示例
M2 判断教师是否有权限申请学院教室：
POST /api/d1/internal/authorize
请求：
{
  "user_id": "101",
  "permission_code": "classroom:apply",
  "resource_college_id": "1"
}


响应：
{
  "code": "OK",
  "message": "success",
  "data": {
    "allowed": true,
    "reason": null
  },
  "request_id": "req-003"
}


约定 reason 可以为 PERMISSION_DENIED、COLLEGE_MISMATCH 或 ACCOUNT_DISABLED。
D1 对调用方验证服务身份；被查询用户身份与目标学院信息要由可信来源确定。
